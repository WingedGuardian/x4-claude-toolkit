### F4 · "nothing was sel-checked" never reaches the skip channel — TOOL BUG · **highest severity**

`_check.py:536` uses `report.add("warn", "skipped", …)` — a **Finding** whose *category string* is
"skipped" — instead of `report.skip(…, degraded=True)`. It never enters `report.skipped`,
`report.degraded` stays empty, and `_cli.py:119` returns **0**.

Proved with `--json` on a mod with zero payload XML:

```json
{ "findings":[{"severity":"warn","category":"skipped",
               "message":"no <diff> file could be read … nothing was sel-checked"}],
  "error_count":0, "skipped":[], "degraded":false }          EXIT=0
```

A mod from which **not one file could be read** yields a machine-readable verdict of *clean,
nothing skipped, not degraded, exit 0*. Any CI consumer parsing this JSON reads a pass.

**Textbook half-fix.** The `Skipped`/`degraded`/exit-3 channel exists for exactly this case, and the
`Skipped` docstring (`_check.py:297`) defines *degraded* as "the skip disabled an ENTIRE check, so a
clean run is not evidence of correctness". The comment directly above the offending line says
*"Nothing examined is a SKIP, never a pass."* **The code does the opposite of its own comment.**

Scope is exactly **2** decoy sites, both in `check_sel_resolution` — the tool's core check — against
**16** correct `report.skip()` sites elsewhere (4 already `degraded=True`):
- `:536` no readable `<diff>` file → whole check disabled
- `:527` `tree may be incomplete: …` → every verdict below computed against an incomplete tree

### F9 · `ask.py` reports output-line count as "hits", inverting its own contract — TOOL BUG · high

`ask.py:119` — `lines = [ln for ln in out.splitlines() if ln.strip()]` … `print(f"{len(lines)}
hit(s)")`. "Hits" is non-blank **output lines**, unrelated to matches:

| query | actual | reported |
|---|---|---|
| `debug_text[@exact]` | 1 file, **2** occurrences | "1 hit(s)" |
| `owner[@faction]` | **4** files, **847** occurrences | "32 hit(s)" |

**The dangerous half:** the denominator guard triggers on `if lines:` being empty, so a
`count()`-shaped query — the natural way to ask "how many" — returns the text `0`, which is one
line:

```
$ ask.py xq 'count(collection("x4raw")//ware[@id="definitely_no_such_ware_xyzzy"])'
0

1 hit(s) in x4raw.          rc=0
```

**Zero matches reported as "1 hit", guard never runs.** The same question as a node sequence behaves
perfectly (`NEGATIVE CONFIRMED over 13672 of 13684 documents`, all 12 exclusions named). The hard
case is done beautifully; the easy case is wrong in a way that bypasses the hard case.

### F10 · `x4compat` is blind to cross-mod nested patches — TOOL BUG

`zzz_personal_overlay_F` exists solely to patch `moreroomsforships`. x4compat:

```
x4compat: 101 mods, 0 shared files examined.
No HARD / UNION-KEY / FULL-OVERRIDE collisions found.        EXIT=0
```

Not a general breakage — the same tool finds 396 shared files and 53 HARD collisions over the full
modlist, and 46 files / 9 HARD for candidate `xspvro`. It is specific to the nested path, and the
mismatch is **double**:

| | vpath |
|---|---|
| overlay ships | `extensions/moreroomsforships/md/morerooms.xml` |
| target owns (inside `ext_01.cat`, 220 members) | `md/MoreRooms.xml` |

Neither the `extensions/<mod>/` prefix nor the case is normalised. x4validate resolves this
correctly under Tier B (0 errors); x4compat does not. **Two tools disagree, and x4validate is
demonstrably right** — the patch works in game. The construct x4compat misses is the single most
collision-prone thing in X4 modding: one mod deliberately overwriting another's file.

### F1 · `_xsd.schema_of()` resolves schemas by basename in `libraries/` only — TOOL BUG

`xsi:noNamespaceSchemaLocation` is relative to the document; the code takes its basename and looks
only in `reference/libraries/` (37 XSDs).

| declared | actually at | tool says |
|---|---|---|
| `../../core/coreaddon.xsd` | `reference/ui/core/coreaddon.xsd` | "not bundled" ×30 |
| `../../ui/core/addon.xsd` | `reference/ui/core/addon.xsd` | "not bundled" |
| `cutscenes.xsd` | `reference/cutscenes/cutscenes.xsd` | "not bundled" |

**Observed live:** `kuertee_alternatives_to_death --tier b --update` printed
`NOT CHECKED: schema check for ui.xml: declared schema 'addon.xsd' is not bundled in
…\reference\libraries`. It **is** bundled. A false reason is the worse half — it stops the next
person checking. All 31 skips pinned in `gates/schema_sweep.py` are false.

**Not a one-liner:** `cutscenes.xsd` exists in **6 layers** (base + 5 DLC), so resolution must be
layer-aware, not a naive relative join.

### F16 · Version catalogs are skipped, and their contents DIFFER — **NEW, needs research, do not fix blind**

Found while verifying F5. `_VERSION_CAT_RE` (`_cat.py:43`) skips any `ext_*vNNN.cat`. Measured:

| mod | `ext_v800.cat` | files only in v800 | files whose **md5 differs** from `ext_01.cat` |
|---|---|---|---|
| `ebi_pirate_chaos_conflict` | 2 XML (`libraries/god.xml`, `libraries/jobs.xml`) | 0 | **2 / 2** |
| `ebi_timelines_faction_use_ship` | 15 XML (ship/weapon macros) | 0 | **15 / 15** |

**Good news:** nothing is *missing* — every v800 path also exists in `ext_01.cat`, so no content is
invisible. **Open question:** all 17 are *different versions* of those files. If the engine prefers
`ext_v800.cat` on X4 ≥ 8.00 (we are on 9.0), then our effective tree holds the wrong revision of
`libraries/god.xml`, `libraries/jobs.xml` and a Timelines carrier's macros.

Same question applies to base-game DLC: `ego_dlc_ventures` ships `ext_v610/v620/v700/v710` and
`ext_01_diff_v900`, and `_iter_mod_cats` selects only `ext_01/02/03`.

**✅ RESOLVED 2026-08-02 — the load rule is EXACT game-version match, and skipping non-matching
version cats is what the engine does too.**

**Documented rule** (official Egosoft Steam Workshop guide, id 245117855): *"the game will search
for a version catalog of the current game version in your extension folder, e.g. version 1.50
would look for ext_v150.cat. If it exists it will be used to override content from your other
extension catalog(s)."* Exact match; `version.dat` = **900**, so `ext_v900.cat` is the only
`ext_vNNN` name the engine would honour today.

**Engine-proven, two independent fingerprints in one debug.txt (2026-08-02 capture):**
1. **Ware-registry proof.** `ebi_timelines_faction_use_ship`'s v800 `libraries/wares.xml` defines
   `ship_tfm_xl_carrier_01_a` (replacing ext_01's `_b`); the engine logs
   `Property lookup failed: ware.ship_tfm_xl_carrier_01_a` — the ware does not exist in the live
   registry, so the v800 wares.xml was never applied.
2. **Line-number proof.** `md/story_research_xen_equipment.xml` exists in BOTH cats and references
   `ware.ship_tfm_xl_carrier_01_a` at lines **11 and 30** in the ext_01 revision but **11 and 26**
   in the v800 revision. The engine's two error lines cite **11 and 30** — it parsed ext_01's copy.

Both proofs agree: on a 9.00 game, `ext_v800.cat` is not opened at all. The "highest vNNN ≤
current" alternative is dead. So for every INSTALLED mod, `_VERSION_CAT_RE`'s skip produces
exactly the tree the engine sees — **no tool defect**; the skip-warning text is the only inaccuracy
(it claims version cats "do not appear in mods" and are "resolved at unpack time into reference\" —
both measured false).

**Residual gap (advisory, base-game only):** `ego_dlc_ventures`' `ext_01_diff_v900.cat` /
`ext_03_diff_v900.cat` match the CURRENT version (exported 19.05.2026, signed). The `_diff_vNNN`
form could not be engine-fingerprinted from this log (its one MD member never ran), but Egosoft
shipping current-dated signed content makes it ~90% live. Consequence measured: `reference\`'s
ventures tree is content-identical to `ext_01` (modulo export comment) and **lacks the v900
deltas** — `libraries/wares.xml` (4 venture wares: icon videos added, shield `use threshold`
0 → 0.31/0.41), `md/cm_chain_secure_resource_fields.xml` (drops a `faction.player.coalition`
expression), 8 asset XMLs in ext_03_diff_v900 (venture fighter/engine/shield macros), plus lua we
don't parse. Tiny blast radius, ventures-only. Any `_cat` change to load current-version cats is a
separate gated decision.

**Consequent upstream-mod finding (both ebi mods — COSMETIC, corrected same day):** their
`ext_v800.cat` is the author's INTENDED 8.0+ content, dead since the 9.00 update because no
`ext_v900.cat` exists — both mods run their pre-8.0 revision. First write-up claimed the carrier
research was silently broken; **measuring the MD file disproved that**: ext_01's
`story_research_xen_equipment.xml` grants BOTH carrier variants (the author left the union of
revisions in), so on 9.00 the `_b` carrier + weapon + engine blueprints all grant correctly and
only the `_a` grant no-ops (the v800 rework was a ware-id rename; `_a`'s component ref is even
the same `ship_tfm_xl_carrier_01_b_macro`). Net effect: **2 cosmetic load-time errors per
session, zero functional loss.** A repair overlay would either be a destructive remove of 2 dead
lines (nothing gained) or would ADD the `_a` ware (a duplicate buildable carrier — a gameplay
change, not a repair). Recorded; no overlay recommended.

### F17 · `x4compat` could not build a base for ANY cross-mod nested patch — TOOL BUG · ✅ fixed `8f74d23`

Logged as "x4compat has no skip channel". **Measuring first showed the skip channel was the smaller
half**, and the plan's framing was wrong.

`_merge._build_owned` locates a cross-mod patch's base by scanning `dlc_dirs() + config.overlays`.
`analyze()` passes a bare `_merge.Config()`, whose `overlays` is empty — so for
`extensions/<owner>/<rel>` the owner was **never** in that list: `owner_dir` None → `base_tree` None
→ `continue` past every mod on the file. Hypothesis confirmed 5/5 against the live install: every
sample returned `tree=None` bare and a real root (`<mdscript>`, `<components>`, `<macros>`,
`<index>`) the moment the owner was supplied as an overlay.

**Blast radius, measured on the live 101-mod install (caller-frame filtered — the first pass was
contaminated by `build_effective`'s own per-DLC-layer calls and had to be redone):**
**140 of 523 examined files** produced no comparison, silently discarding **144 `<diff>` mods** across
10 mods (`ship_variation_expansion_vro` 62, `cpsdo_vro` 43, `cpsdo_faction` 19, …). So x4compat could
not analyse a single cross-mod nested patch. F10 made those 127 extra files *visible*; every nested
one landed in the drop.

**Fix:** stage only the OWNER as an overlay — never the other patchers, so every mod's `sel=`
resolves against the same unpatched base exactly as the non-nested path does (pinned by
`test_owner_overlay_does_not_apply_the_other_patchers`). Then the channel F17 actually asked for:
`CompatReport.skipped`/`.degraded`, a `NOT ANALYSED` section, exit 3 — with the reason **computed**
per case, not guessed (a draft hard-coded "the owning mod is not installed" for every nested path;
the F1 lesson says a wrong reason is worse than none).

**After: 140 → 7 unanalysable files.** Collision counts unchanged at 55 hard-ish / 3 union-key /
217 soft, and that is the *correct* result: 127 of the 134 recovered vpaths have exactly one
patcher, and one patcher cannot collide. Verified rather than assumed.

### F18 · An element and its own attribute are unrelated node ids — **✅ FIXED 2026-08-02** (`4ffd3ab`, with F12)

`_canonical` keys an attribute as `<element path>/@name`, a different string from the element's own
path. So mod A `<replace sel=".../explosiondamage/@value">` and mod B
`<replace sel=".../explosiondamage">` (replacing the whole element) never registered as a
collision, though whichever loads last plainly wipes the other. (Found twice on 2026-08-01: live —
`ship_variation_expansion_vro` vs `zzz_personal_overlay_G`, a deliberate guarded repair — and in an
F17 test fixture.)

**Fixed as the new kind `SUBTREE`, order-aware by construction:** a later-loading mod
replace/removing an ELEMENT collides with every earlier mod's edit strictly inside it (attribute or
descendant). A wipe that loads FIRST is excluded — it merely changes what the victim's `sel` sees,
which the Tier B sel check already covers. The order filter proved itself during measurement by
correctly clearing `ebi_m0_vro`: it looked like a victim of VRO until its `ws_1696862840` dependency
was checked — it resolves against the installed VRO and orders the mod after the wipe.

**Measured: 184 raw pair-hits → 165 real clobbers → 153 collision rows**, dominated by `vro`'s
wholesale `<replace sel="/macros">` wiping `pdrealisticboosters`' boost tweaks across ~100 engine
macros, plus `vro` wiping `ebi_timelines_faction_use_ship`'s people/capture edits on kha/xen ships
and `xspvro` wiping `distances` (god.xml ×5), `vro` (jobs ×2) and `X4CapturableXenonXL` (wares ×2).
Every sampled row is a true "later mod destroys earlier mod's applied change" statement. Counts as
**hard-ish by user decision** (hard-ish 55 → **208**), with the load-order-is-convention caveat in
every row's detail text.

### F19 · Tier B blesses a bare-path cross-mod patch the engine ignores — TOOL BUG · **FALSE OK, highest severity**

**A false OK is the one failure class this toolkit exists to prevent, and Tier B has one.**

KNOWLEDGEBASE "Patching ANOTHER extension's file" (verified 2026-07-06) says a diff against another
MOD's file must be nested at `<yourmod>/extensions/<target>/<rel>`; a bare mirrored path is the
base-game form. `x4validate --tier b` does **not** enforce that: for a plain vpath,
`build_effective` lets an installed mod's full file become the base and a later mod's diff apply on
top. `zzz_personal_overlay_E` ships 7 diffs at bare paths for files owned by `cpsdo_zb_modpack` and
Tier B reports **0 errors, exit 0**.

**Engine evidence (`debug.txt`, 2026-07-26 12:42; the 7 files were deployed 2026-07-24 23:01, so the
timing confound is ruled out).** The engine emits a signature-failure line per loaded extension file
— 6,144 of them, 3,454 under `assets/`, 1,455 under the nested `extensions/` form. Within one
author's own mods:

| file | form | logged? |
|---|---|---|
| `zzz_personal_overlay_E\libraries\factions.xml`, `\libraries\jobs.xml` | base-game path | ✔ loaded |
| `zzz_personal_overlay_E\assets\…\*_macro.xml` ×7 | bare path over another mod | ✘ **never** |
| `zzz_personal_overlay_G\extensions\ship_variation_expansion\…\caiman_macro.xml` | nested | ✔ loaded |

The "line is per-vpath, not per-file" alternative was tested and killed: **356 distinct relative
paths are logged for 2+ different mods** (up to 40 mods for one `t/0001.xml`), so the line is
per-file and the silence is informative.

**Why the oracle gate cannot catch this:** `oracle.py` replays ops the engine *rejected*. An op the
engine never loaded produces no error line at all, so a failure-only log is structurally blind to
it — precisely the limit `oracle_index.py` already prints about itself.

**✅ FIXED 2026-08-01, both phases, after the blast radius was measured (101 installed mods):**
1,531 bare-path diffs with a real base+DLC file (81 mods, must stay untouched) · 33 `t/*.xml`
synthetic-language diffs (the false-positive trap class) · **7 true positives, all in
`zzz_personal_overlay_E`** · 16 no-source diffs (already erroring, must not double-report).

**Phase 1 — the gate.** `MergeResult.base_from_game` records whether the base came from the GAME
(reference/, a DLC layer, or the synthetic `<language>` root) — the distinction `base_found`
loses (`_merge.py`: `base_found or mode in {"union","full"}` conflates "the base game has it"
with "somebody has it"). `check_sel_resolution` fires a new `_inert_bare_path_finding` (ERROR,
category `path`) when the path is plain, `base_from_game` is False and some mod supplies the
tree — naming the supplier and the exact `extensions/<owner>/<rel>` path to move to, and
deliberately skipping `_check_ops` (an op verdict on a file the engine never opens is noise).
Measured: `zzz_personal_overlay_E` Tier B **0 err exit 0 → 7 err exit 1**.

**Phase 2 — the tree** (measured first: the over-permissive merge put **14 lied attribute values**
in the effective tree — e.g. XL shield recharge rate 425 where the engine uses 589, capacity
253,812 vs true 194,385). `build_effective` now REFUSES a mod-shipped `<diff>` at a bare path when
`from_game` is false, recording `<mod>:diff(inert)` in sources and adding nothing to provenance.
Full non-diff files still override cross-mod (the engine's VFS honours those — `cpsdo_vro`
clobbering `cpsdo_zb_modpack` weapon-fx macros is live proof). The decision is load-order
independent: reference/ and `t/` are decided upfront and DLC layers precede mods in
`overlay_dirs`. DLC-shipped diffs are exempt. Re-measured after: **14 → 0 lied values**.

**Verified (both phases):** suite 291 → **303**, 12 new tests each mutation-verified · trap seed
**T14** (`dev\zz_audit_trap`, bare diff over `cpsdo_zb_modpack` content): Tier A 7→8, Tier B 8→9 ·
101-mod sweep exactly 7/1/0 before AND after phase 2 · oracle 234/234 · oracle_index 12/12 ·
schema_sweep exact baseline · regress: old-vs-new diff shows ONLY the two predicted rows, and the
phase-2 run is **byte-identical** to the phase-1 run · x4compat whole-install run byte-identical
old-vs-new (55 hard-ish / 3 UNION-KEY / 217 SOFT; the "8 unanalysable" vs F17's recorded 7 predates
F19 — the 8th is `cpsdo_faction`'s unparseable `t/0001-l088.xml`, counted under a different
denominator by F17) · x4effective `dump` shows engine truth with
`zzz_personal_overlay_E:diff(inert)` visible in sources but absent from provenance.

**Engine-rule confidence 96%** (upgraded from 85% during due diligence): the same-rel-path triple
in debug.txt — `ship_cpsdo_s_hengdao_01_macro.xml` supplied by `cpsdo_zb_modpack` (logged),
patched nested by `cpsdo_faction` (logged AND its op evaluated: `[=ERROR=] No matching node …

**Upgraded to 99% on 2026-08-02:** after the repair moved the same 7 files to the nested form, a

**Follow-up:** BaseX's `x4eff` DB is built from `build_effective` and is stale until rebuilt

### F7 · `xsd-strict` conflates two classes and excuses both — **✅ FIXED 2026-08-02** (`f9636af`, with F14)

All non-gating schema complaints were labelled *"md.xsd stricter than the engine"*. Two different
things were merged:

1. **Genuinely stricter** — the `[facet 'pattern'] '[A-Z][A-Za-z0-9_]+'` naming complaints against
   `kuertee_atd`; kuertee's lowercase names demonstrably work.
2. **Attribute unknown to schema *and* absent from vanilla** — `attribute 'X' is not allowed`.

Class 2 does not fit the excuse: there is nothing for the schema to lag.

**Fixed as designed, with one measurement-driven upgrade:** the check is at
**(element, attribute) pair granularity**, not name granularity — and that turned out to be
load-bearing. `category/@matchextension` (3 findings, `ebi_timelines_faction_use_ship`) is a *real*
attribute on the *wrong element*: vanilla uses `matchextension` 140 times, every one on
`<location>`, so a name-level lookup (969 corpus hits incl. base) would have excused a genuinely
dead patch. The other 5 are `element/@forkmaterial` — invented by VRO, 4 corpus occurrences, all
VRO itself. `_xsd.dead_attr` gates as ERROR, category `schema-dead-attr`, over a memoized
vanilla+packed-DLC pair index.

`xsd-unknown-attr` but **stays INFO** — MD attributes can be spawn-time engine features no static
pass or debug.txt can settle, and the four `kuertee_atd` attributes were explicitly left unresolved
by the user (F8). Pinned by `test_md_side_dead_attr_is_categorized_but_never_gates`, whose docstring
says failing it is a decision to re-litigate with the user, not a cleanup.

Total F7+F14 movement: **15 findings INFO→ERROR across 3 third-party mods**, each verified
individually real; `schema_sweep` re-quoted 45→60 / 91→76 with every other bar unchanged.

### F15 · `x4xref` signal→param join — **❌ MEASURED AND DROPPED 2026-08-02** (was: GAP · highest value)

The pitch: `md_xref.tsv` already carries signal/event/cuedef rows; join *"does a reader of
`event.param.Y` correspond to a signal site that passes `param=`?"* — both halves of the July ATD
ransom bug are that shape.

**The measurement spike (3 passes, 467 MD scripts / 23,518 cues / 16,261 signal sites, 0 unreadable)
killed it.** Each pass eliminated a named confound; the vanilla count stayed high for a structural
reason:

| pass | rule | vanilla+DLC flags | what it disproved |
|---|---|---|---|
| 1 | no-param site → listener reads `event.param` | **229** (190 bare / 39 `@`) | raw rule drowns; Simple_Menu_API idiom alone = 850+ mod flags |
| 2 | … excluding `event.param?`-guarded listeners | **229** (0 guarded!) | guards are NOT vanilla's tolerance mechanism |
| 3 | listener-centric: chain-reads `event.param.X` AND **all** literal callers param-less | **64** (53 bare / 11 `@`) | the residual is structural, not tunable |

**Why pass 3 is the verdict:** (a) `event.param` is a built-in event property that is NULL, not
missing, on a param-less signal — plain reads never error, only CHAINED reads fail, so the rule was
already at its tightest useful form. (b) The surviving vanilla cluster (~40 Timelines scenario
`Start` cues) is fed param-less by a *literal* `setup.xml` signal while the real param-passing
feeders are **variable-target signals** — and 1,033 vanilla sites (8%) are unresolvable variables.
The param-passing path is systematically the dataflow path. (c) The ATD bug itself had a variable
target (`$getPlayerPropertiesCallback`) — **the rule misses its own motivating case while flagging
64 vanilla cues.** Wrong on both edges; dataflow was excluded from scope by design and is the only
thing that would fix both.

Dropped per the pre-committed criterion (same as the W3.3 MD-ordering lint). Do not re-propose
without a dataflow design. No index change was made; `md_xref.tsv` is untouched.
