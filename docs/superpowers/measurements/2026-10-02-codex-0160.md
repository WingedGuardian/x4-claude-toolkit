## Results

### P6 -- exit 2 + stderr reason (the key question): FAIL-OPEN. Plan-changing: no (the design already ignores exit 2), but the conflict C8 is resolved in favour of the measurement.
- Prediction: BLOCKS (the source says so). **WRONG.**
- Command: a `PreToolUse` hook that exits 2 with a stderr reason when the payload contains `EXIT2ME`; the model was asked to run `New-Item -ItemType File EXIT2ME.flag`. Two independent hook implementations: (a) python `sys.exit(2)` after writing stderr (run1, p1); (b) a `.cmd` that drains stdin, echoes to stderr and does `exit /b 2` on EVERY tool call (run2, p2).
- Result, MEASURED 2 of 2: the flag file WAS created, the command ran, and the status line was `hook: PreToolUse Failed`. Controls in run1: a JSON `permissionDecision:"deny"` gave `hook: PreToolUse Blocked`, the error "Command blocked by PreToolUse hook: probe json deny. Command: ...", and the flag was NOT created (1 of 1); the ALLOWME call ran (1 of 1). So the subject can express a block, and exit 2 still did not block.
- Changes the plan? The four Codex output shapes never use exit 2, so no. But: any hook crash, non-zero exit, bad quoting or unparseable output is `Failed` and **the command runs (fail-open)**. The only blocking channel is the parsed JSON deny. The source (READ) says exit 2 blocks and the measurement says it does not; trust the measurement, and treat a source/feature-flag difference as INFERRED.

### P4 -- write_stdin: NOT SEEN (partly inconclusive). PLAN-CHANGING.
- Prediction: a `write_stdin` PreToolUse fires. **Not observed.**
- MEASURED 1 run: the model started `python -i` through `exec_command` (tty) and sent `print(40+2)` and `exit()` through `write_stdin` (it reported both tools, "called through functions.exec", a code-mode wrapper). Result: exactly ONE PreToolUse (Bash, `python -i`) and one PostToolUse; **0 PreToolUse events for 2 write_stdin calls**; the REPL did receive the input (it printed 42).
- Caveat (INFERRED): because the calls went through the `functions.exec` wrapper, a direct non-wrapped `write_stdin` was not exercised; that path is UNMEASURED. Fixture: `bash_exec_command_tty.json` (the `python -i` start).
- Plan change: YES. Task 4's `write_stdin` branch and decision 5 ("`write_stdin` text with a newline is checked as a shell command") have no observed trigger. It is also a bypass: start an interactive shell with an innocuous command, then type the dangerous command through stdin; the hook sees only the first. Disclose it as a coverage gap, and the user may choose to make the guard refuse tty/interactive shell starts (`pwsh`, `cmd`, `bash -i`, `python -i`). Needs a decision.

### P7 -- bash under cmd from PowerShell: CONFIRMED. PLAN-CHANGING (supports decision 3).
- Method: PowerShell tool, PATH rebuilt from the registry (Machine + User), `SHELL`/`MSYSTEM` unset. `Get-Command bash -All` = `C:\Windows\system32\bash.exe` (the WSL stub), then `...\WindowsApps\bash.exe`; Git's bash is absent.
- Hook `bash <abs>/b.sh` (SessionStart): **Failed, the script did not run**. Control: the same project launched from Git Bash (Git `bash.exe` first on PATH) ran it, `BASH_VERSION=5.2.37 OSTYPE=msys` (2 of 2 runs). So `bash` resolves by the PATH order of whoever launched Codex.
- Plan change: a `bash "..."` hook entry on Windows is not safe, and since a Failed hook means the command runs, the wrong shell is a silent fail-open. Use the pwsh/powershell entry on Windows (decision 3 stands, now measured).
- Working Windows hook forms (MEASURED, 1 run each unless stated):
  - `pwsh -NoProfile -File <path> || powershell -NoProfile -File <path>`: ran (pwsh 7.6.6). **Fallback proven**: with a nonexistent first program, `powershell` (5.1.26100) ran. A path CONTAINING SPACES works when double-quoted AFTER the program name (`-File "<dir>/sp ace/t.ps1"`): 2 of 2.
  - `cmd /C "<path>/t.cmd Q5"` (no spaces) and `<path>/t.cmd U3` unquoted: ran.
  - `pwsh -NoProfile -Command "Set-Content ..."`: ran.
  - Unquoted `<abs>/python.exe <abs>/script.py`: ran.

### P12 (added) -- hook command quoting: PLAN-CHANGING for the hook entry text
- Prediction (made after the first failure, not before): a leading `"` breaks it. MEASURED: 3 of 3 commands starting with a double quote failed (`"t.cmd" Q2`, `"python.exe" "script.py"`, `"<spaced path>/t.cmd" Q9`); 0 of 6 commands not starting with a quote failed. Also failed: `cmd /C ""<spaced path>/t.cmd" Q8"` and `cmd /S /C ""..." Q10"` (2 of 2).
- Consequence: the game root is under `C:\Program Files (x86)\...` (spaces), so the Windows entry must be `pwsh -NoProfile -File "<path with spaces>" || powershell -NoProfile -File "<path>"` (program name first, quoted argument after). A bare quoted path as the first token is dead and fails open. A test must assert the rendered command does not start with `"`, and Task 13 should run a spaced path live.

### P8 -- subdirectory start: MATCHES

Controls: `git status --short` ran (3 of 3); `git add a.txt` was not rule-rejected (it failed on the sandbox's `.git/index.lock` Permission denied).
- Untrusted-project behaviour: **UNMEASURED.** `-c projects.'<path>'.trust_level="untrusted"` changed nothing, and Codex still wrote `trust_level = "trusted"` for the folder (see finding 2). Task 8's disclosure about untrusted projects stays INFERRED. Plan change: none.

## Other findings (not in the probe table)

1. **Hooks inherit the FULL parent environment on 0.160.0** (MEASURED 1 run, by dumping `set` from a hook): CLAUDE*, X4_TOOLKIT, X4_NEXUS_KEY, PATH and the rest were present. C5 said `env_clear()` plus a snapshot; in practice the snapshot is the whole environment. Consequences: `X4_TOOLKIT` set in the user environment IS visible to a `.codex/hooks` copy (helps C15), and a hook can read secrets, so a guard must never log its environment. (I deleted my dump file because it held the Nexus key.)
2. **Codex appends trust entries to the global `~/.codex/config.toml`.** MEASURED: the `[projects.*]` table count went 20 -> 21 during the p5 run alone, and every scratch folder I ran in (p0, p1, p2, p4, p5 and others) now has `trust_level = "trusted"`. I did not edit that file; these are Codex's own writes, all under `plan2/measureB/`. Plan impact: `codex exec` in a folder trusts it permanently, which the E2E notes and the installer README should say. The user may want to prune the roughly 15 scratch entries.
3. Every failure mode (exit 1 or 2, crash, wrong shell, bad quoting) shows `PreToolUse Failed` and the command runs. Only a parsed JSON deny shows `Blocked`.
4. In a Codex workspace-write sandbox `git add` fails on `.git/index.lock`, so a deny-rule test must not use `git add` success as its control.

### 2026-10-03 M10-additionalContext-cap -- MEASURED (one `codex exec` run, decision J-Q4)

**Status: RUN 2026-10-03, codex-cli 0.160.0, rc 0, one run.** Result below the harness description.

Question: how many characters of a hook's `additionalContext` (PreToolUse) and of a
SessionStart hook's plain stdout reach the model? The toolkit bounds its own output at 10,000
characters (`X4_HOOK_MAX_CHARS`) "until measured (M10)"; this run says whether that bound is
(a) needed and (b) sufficient on Codex.

Harness (session scratchpad `m10/`, not committed): `emit.py` is the hook. Its k-th PreToolUse
call emits `additionalContext` of 8,000 / 16,000 / 32,000 / 64,000 / 128,000 characters,
framed `M10-HEAD-<size>-<nonce>` ... `M10-TAIL-<size>-<nonce>` with a fresh 8-hex nonce, and no
`permissionDecision`. SessionStart prints 40,000 characters with its own nonces. Nonces and
each payload's `transcript_path` go to `m10/state/`, outside the Codex root. `emit.ps1` wraps it in
the shipped hook's proven shape (`pwsh -NoProfile ... -File "<abs>\emit.ps1" <event>`; no
command starts with `"`). `mkroot.py` writes `m10/root/.codex/hooks.json`. `run.py` makes the
run (stdin DEVNULL, timeout 600, refuses a second run). `readout.py` scores it. `emit.py` was
checked offline with fixture payloads: 8,000 chars out with HEAD and TAIL, and 40,004 bytes for
SessionStart.

The exact command (from Git Bash; `python <SCRATCH>/m10/run.py` does the same):

    codex exec --dangerously-bypass-hook-trust -s workspace-write --skip-git-repo-check -C "<SCRATCH>/m10/root" "Run these five shell commands one at a time, waiting for each: echo m10-1, echo m10-2, echo m10-3, echo m10-4, echo m10-5. Then list, verbatim, every token beginning M10-HEAD or M10-TAIL that you can see anywhere in your context, one per line, and nothing else." </dev/null

Readout (`python <SCRATCH>/m10/readout.py`): PRIMARY = each HEAD/TAIL nonce looked up in the
rollout JSONL at the recorded `transcript_path`, plus any truncation or spill marker. SECONDARY
(model-reported, labelled as such) = the nonces quoted in the final answer. The nonces are
random, so the model cannot guess them. ASSUMED: the rollout records what the MODEL received;
if the two readouts disagree, the quoted nonces win for "in context", and the disagreement is
recorded.

Prediction (INFERRED from the spec's "spills to disk past some size"): 8k and 16k intact; a cap
or spill somewhere in 32k-128k.

| size (chars) | event | rollout HEAD / TAIL | model HEAD / TAIL | what reached the model |
|---|---|---|---|---|
| 8,000 | PreToolUse | yes / yes | yes / yes | all 8,000 chars, no warning |
| 16,000 | PreToolUse | yes / yes | yes / yes | ~10,100 chars: head + tail, **1,539 tokens cut from the middle** |
| 32,000 | PreToolUse | yes / yes | yes / yes | ~10,100 chars, 5,539 tokens cut from the middle |
| 64,000 | PreToolUse | yes / yes | yes / yes | ~10,100 chars, 13,539 tokens cut from the middle |
| 128,000 | PreToolUse | yes / yes | yes / yes | ~10,100 chars, 29,539 tokens cut from the middle |
| 40,000 | SessionStart | yes / yes | yes / yes | ~10,100 chars, 7,540 tokens cut from the middle |

**Result (MEASURED, codex-cli 0.160.0, Windows):** Codex keeps about **2,460 tokens (~10,000
characters) of each hook-injected text**, PreToolUse `additionalContext` and SessionStart stdout
alike. Past that it keeps the HEAD and the TAIL and replaces the MIDDLE with `...N tokens
truncated...`, prefixed by `Warning: truncated output (original token count: N)` (tokens counted
as chars/4 here). Read from the rollout JSONL; the model's own quoted list agreed on every nonce.

⚠ **The harness's own readout was WRONG, and the near-miss is the lesson.** `readout.py` scored
only the HEAD/TAIL markers, so it printed "True/True" for every size -- "no cap up to 128K".
Middle truncation preserves exactly the two things it looked at. The cap was found only by
reading the rollout text for the `truncated` markers the readout listed but did not explain. A
probe framed at the ends cannot see a loss in the middle; frame the middle too.

**Implication for `X4_HOOK_MAX_CHARS` (10,000):** the bound is NEEDED on Codex (larger output is
cut) and roughly SUFFICIENT: Codex's cap sits at about the same size. An output at exactly
10,000 chars may lose a few dozen characters from its middle on Codex. The existing rule --
print the DIRECTIVE FIRST -- holds on both agents; Codex additionally keeps the tail. No code
change made on this result.
