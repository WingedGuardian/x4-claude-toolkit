[b]This toolkit ships with all of that already solved[/b] -- plus a suite of X4-specific tools, written for this environment, that answer questions no off-the-shelf tool can.
 
+[color=#e06666][size=5][b]New in v3.1 -- the guard that inspects every command got taken apart[/b][/size][/color]

+[b]Two ways to walk past every hard block. Upgrade for these two if for nothing else.[/b] Both were in the same place: how the guard works out [i]which command[/i] it is actually looking at. A rule keyed on a command's name is only as good as that name, so a wrong answer there does not cost you one rule -- it costs you every rule keyed on a name, all three hard blocks included.
+
+The first: a wrapper flag whose value is a word became the command name. A delete aimed at your game folder behind [font=Courier New]env -u VAR[/font] or [font=Courier New]sudo -u root[/font] came back ALLOWED, while the same delete written plainly was correctly blocked. Two similar-looking commands [i]were[/i] blocked -- by accident of their argument shape -- which is exactly what kept the gap invisible. The second: quoting a single token in front of a command short-circuited the whole resolver, and [b]7 of 9[/b] rules flipped from firing to ALLOW. The two rules that did [i]not[/i] flip are the two that are not keyed on a command name, which is what pins the cause.
+
+[b]And the guard could be hung by ordinary shell.[/b] A variable that names itself re-expands every reference on every pass -- a clean 9x each time -- so a four-character token reached [b]7.7 MB[/b] inside the loop's own five passes, and one real 949-character command from this machine's history became [b]18.3 GB[/b] of working set with a game running. That is the blocking path, so it hangs the whole session. It needs no adversary; a self-referential assignment is ordinary shell. Every neighbouring bound was sensible on its own and none of them bounded [i]size[/i]: a product of individually sensible bounds is not a bound.
+
+[b]61% of the guard had never been fuzzed, and the run said nothing about it.[/b] The fuzzer derived its rule list from the policy file and refused below a rule-count floor -- but never asked how many of those rules any test case actually reached. Fourteen had none at all, two of them hard blocks, while it printed a healthy mutant count and "no bypass found". The new seeds immediately found real bypasses in rules that had shipped and were being relied on. A bug history is not a specification: the shapes nobody had tested were untested precisely because they had not bitten yet.
+
+[b]The installers were audited the same way, and it was not pretty.[/b] [font=Courier New]--dry-run[/font] performed a real install in place -- both installers, both methods, exit code 0, "install complete" printed. The source machine's secrets travelled: the backup and temp siblings of the path config, which hold your Nexus API key by construction, were copied into the destination. The global install method on Windows was completely broken and had shipped that way. The safety gate that refuses to overwrite your files listed skills this toolkit does not ship, so your own [font=Courier New]x4-[/font]something folder was reported as a file the install would replace. An indented setting in the path config beat the real one, so re-installing with a new game path silently kept the old one.
+
+[b]x4stats was telling five mods they changed nothing.[/b] It found a ware only when a [font=Courier New]<ware>[/font] element appeared as a patch payload, so the default X4 idiom -- a [font=Courier New]sel=[/font] pointing at a ware that already exists -- was invisible. Measured over a 125-mod install: 37 mods edit wares and [b]5 reported "changes no wares", all five wrong[/b], the largest hiding 1,443 operations. Now one reports zero, and that one is right (every one of its operations is a removal). Unattributed operations fell from 3,414 to 190, and 187 of those 190 are operations the engine itself would not apply.

All nine are fixed, each proven to go red against the exact defect it is supposed to catch.

Nobody read them. Clearing that unmasked three more things it had been hiding, each one invisible until the one in front of it was fixed.

+[b]The worst of them: [font=Courier New]install.ps1[/font] was 100% dead on Linux and macOS[/b] -- both install methods, and v3.1.0 shipped it that way. Then the guard rule added in v3.1.0 to close a total bypass of all three hard blocks turned out to be the one rule nothing ever tested -- and given a test, it failed one immediately: a command name with a substitution buried inside a path, aimed at your game folder, was ALLOWED, while the plain spelling was correctly blocked. After that, the release bundler refused to package a correct release, and the test suite's own skip limit failed a run that had zero failures.

A green that could not have gone red was never a green.

+Turns X4's own [font=Courier New]debug.txt[/font] into a triage: every error line bucketed and attributed to a mod, with the buckets required to sum to the input so nothing is quietly dropped. Crosscheck mode compares what the engine skipped against what the validator predicted, [i]per item[/i] -- and "the engine hit it but we never predicted it" is a validator blind spot, which is how a fair number of the fixes in this changelog were found.
