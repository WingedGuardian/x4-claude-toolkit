[color=#e06666][size=5][b]What Is This?[/b][/size][/color]

[url=https://claude.ai/code]Claude Code[/url] is an AI assistant by Anthropic that runs directly on your computer. Unlike ChatGPT or a regular Claude chat, it can [b]read your files, run commands, edit configs and execute scripts[/b] -- all with your permission. Think of it as a modding expert sitting next to you who can actually touch your files.

X4 modding is full of [b]silent[/b] failure modes. A diff patch whose [font=Courier New]sel=[/font] matches nothing validates clean, loads clean, and does nothing. A multi-file change forgets one file and the ware never appears. Another mod quietly overwrites the value you just set. None of it crashes; it just doesn't work, and you find out an hour into a playthrough.

Most people who try to use an AI assistant for modding spend days wiring up tools, explaining the engine, and building guardrails so it doesn't wreck their install. [b]This toolkit ships with all of that already solved[/b] -- plus a suite of X4-specific tools, written for this environment, that answer questions no off-the-shelf tool can.

[color=#e06666][size=5][b]New in v3.1 -- the guard that inspects every command got taken apart[/b][/size][/color]

[b]Two ways to walk past every hard block. Upgrade for these two if for nothing else.[/b] Both were in the same place: how the guard works out [i]which command[/i] it is actually looking at. A rule keyed on a command's name is only as good as that name, so a wrong answer there does not cost you one rule -- it costs you every rule keyed on a name, all three hard blocks included.

The first: a wrapper flag whose value is a word became the command name. A delete aimed at your game folder behind [font=Courier New]env -u VAR[/font] or [font=Courier New]sudo -u root[/font] came back ALLOWED, while the same delete written plainly was correctly blocked. Two similar-looking commands [i]were[/i] blocked -- by accident of their argument shape -- which is exactly what kept the gap invisible. The second: quoting a single token in front of a command short-circuited the whole resolver, and [b]7 of 9[/b] rules flipped from firing to ALLOW. The two rules that did [i]not[/i] flip are the two that are not keyed on a command name, which is what pins the cause.

[b]And the guard could be hung by ordinary shell.[/b] A variable that names itself re-expands every reference on every pass -- a clean 9x each time -- so a four-character token reached [b]7.7 MB[/b] inside the loop's own five passes, and one real 949-character command from this machine's history became [b]18.3 GB[/b] of working set with a game running. That is the blocking path, so it hangs the whole session. It needs no adversary; a self-referential assignment is ordinary shell. Every neighbouring bound was sensible on its own and none of them bounded [i]size[/i]: a product of individually sensible bounds is not a bound.

[b]61% of the guard had never been fuzzed, and the run said nothing about it.[/b] The fuzzer derived its rule list from the policy file and refused below a rule-count floor -- but never asked how many of those rules any test case actually reached. Fourteen had none at all, two of them hard blocks, while it printed a healthy mutant count and "no bypass found". The new seeds immediately found real bypasses in rules that had shipped and were being relied on. A bug history is not a specification: the shapes nobody had tested were untested precisely because they had not bitten yet.

[b]The installers were audited the same way, and it was not pretty.[/b] [font=Courier New]--dry-run[/font] performed a real install in place -- both installers, both methods, exit code 0, "install complete" printed. The source machine's secrets travelled: the backup and temp siblings of the path config, which hold your Nexus API key by construction, were copied into the destination. The global install method on Windows was completely broken and had shipped that way. The safety gate that refuses to overwrite your files listed skills this toolkit does not ship, so your own [font=Courier New]x4-[/font]something folder was reported as a file the install would replace. An indented setting in the path config beat the real one, so re-installing with a new game path silently kept the old one.

[b]x4stats was telling five mods they changed nothing.[/b] It found a ware only when a [font=Courier New]<ware>[/font] element appeared as a patch payload, so the default X4 idiom -- a [font=Courier New]sel=[/font] pointing at a ware that already exists -- was invisible. Measured over a 125-mod install: 37 mods edit wares and [b]5 reported "changes no wares", all five wrong[/b], the largest hiding 1,443 operations. Now one reports zero, and that one is right (every one of its operations is a removal). Unattributed operations fell from 3,414 to 190, and 187 of those 190 are operations the engine itself would not apply.

[b]Nine of the toolkit's own tests could not fail.[/b] A review pass deliberately broke the code and measured that [b]four already-fixed defects could be put back with the entire suite green[/b] -- so the suite was not merely missing new bugs, it was not holding this release's own repairs in place. All nine are fixed, each proven to go red against the exact defect it is supposed to catch.

[b]v3.1.1 follows immediately, and it is the more uncomfortable half.[/b] The fuzzer described above [i]refused to run at all[/i]: a control it plants to prove it can still fail had been orphaned by a routine refactor, so it exited with an error for everyone, and both continuous-integration legs were red on the v3.1.0 tag. Nobody read them. Clearing that unmasked three more things it had been hiding, each one invisible until the one in front of it was fixed.

[b]The worst of them: [font=Courier New]install.ps1[/font] was 100% dead on Linux and macOS[/b] -- both install methods, and v3.1.0 shipped it that way. It looked for Git Bash in a Windows-only folder and crashed before reaching its first decision. [b]If you are on Linux or macOS, use [font=Courier New]install.sh[/font][/b]; it was never affected. Then the guard rule added in v3.1.0 to close a total bypass of all three hard blocks turned out to be the one rule nothing ever tested -- and given a test, it failed one immediately: a command name with a substitution buried inside a path, aimed at your game folder, was ALLOWED, while the plain spelling was correctly blocked. After that, the release bundler refused to package a correct release, and the test suite's own skip limit failed a run that had zero failures.

[b]They all hid in the same place, and that is the part worth telling you.[/b] The Linux side of continuous integration was marked [i]experimental[/i], which means its result was reported and then ignored -- so a run with a red Linux leg still concluded [i]success[/i], and every fault above passed as a green release. That flag is now off. Two Linux-only checks, including the bash installer's global method and the clean-clone verification, are enforced from this version on. A green that could not have gone red was never a green.

[color=#e06666][size=5][b]Also new in v3.0 -- ask the running game, and a guard that turned out to be walkable[/b][/size][/color]

[b]The toolkit can now query a live game session.[/b] It ships a small optional game extension that opens a channel to X4 while it is running, so "what does the engine actually say this ship's hull is, in my save, right now" becomes a query instead of an inference. Every other tool here reasons about what the merged tree [i]should[/i] produce; this one reads what the engine [i]did[/i] produce -- and the two disagreeing is precisely the case worth finding. It is also how several of the defects fixed in this release were caught.

[b]If you also mod Skyrim: this is our much weaker [url=https://www.nexusmods.com/skyrimspecialedition/mods/181326]DevBench[/url].[/b] alandtse's DevBench is the mature version of this idea -- a proper programmatic interface to a running Skyrim over MCP or HTTP, which runs console commands and reads their output back, calls functions and gets return values, and drives scripted test scenarios in the live game. [font=Courier New]x4live[/font] does considerably less than that today: it reads live state, and that is most of what it does. It is aimed in the same direction, it is under active development, and DevBench is the standard we are measuring it against. If you mod both games, go and look at it -- it is the better tool, and it isn't ours.

[b]The honest half of a major version.[/b] The safety guard that inspects every command was walkable. A delete aimed at the game folder, wrapped in one particular shell form, came back ALLOWED -- while the same delete written plainly was correctly blocked. One line was doing a substring search where it meant whole-word matching. That was live while 996 generated test cases, 82 mutation probes and 388 unit tests were all green, because the generator built to find exactly this could not produce that shape by construction. An instrument's blind spot is usually written into its own design.

Fixed, and the generator rebuilt to vary the [i]shape[/i] of a command rather than replay the bugs we already knew about. The fix was then re-checked against 13,503 real commands from actual sessions: [b]8 verdicts changed, every one stricter, none looser[/b] -- including two that had been quietly allowing a recursive delete inside the game install.

[b]Also fixed, and this one is a data bug rather than a reporting one:[/b] the merged tree was discarding base-game content for DLC files, so a question as ordinary as "what rooms exist" came back with the wrong answer.

[b]Protection for the files you cannot get back.[/b] During development the toolkit's own hand-built mod registry was destroyed four times in twelve days -- never once by a decision, always by a command that ran, resolved to a real path, and met nothing in the way. Irreplaceable files are now marked read-only (measured over 14 write methods, each paired with a control proving it still works when unlocked: [b]11 blocked on Windows, 9 on Linux/macOS[/b], with the gaps documented rather than glossed), a session-start check refuses to continue if one has been emptied or deleted, and the registry save is atomic and refuses to shrink.

[b][color=#e06666]Note:[/color] the command guard now requires Python[/b] -- already needed by the bundled tools. Without it the guard [i]asks[/i] rather than silently allowing.

[color=#e06666][size=5][b]Also new since v2.7 -- 2.8 and 2.9 never came to Nexus[/b][/size][/color]

[b][font=Courier New]x4save[/font] -- read a savegame, and say what removing a mod would silently cost you.[/b] Saves are gzipped XML and far cheaper to query than their size suggests. Two findings worth having even without the tool: a mod's presence in a save's patch block is [i]not[/i] a record of what loaded -- it is the save-baked set, which was 3 of 121 mods on a real list -- and removing a mod leaves no loud dangling references, because the engine deletes the orphaned content silently. In one measured case 37 macros vanished and the log carried a single line about it.

[b][font=Courier New]x4diff --base[/font] -- three-way diff.[/b] Built for "I edited this mod months ago and the author just updated it": it separates your changes from upstream drift, instead of showing you one merged wall of differences.

[b]A patch that patches another mod is finally checked.[/b] Nested cross-mod script patches were validated by nothing at all, and a mod shipping its own [font=Courier New]md/[/font] or [font=Courier New]aiscripts/[/font] used to read as a clean pass.

[b][font=Courier New]x4modlist tracked[/font][/b] -- what your Nexus account follows, set against what you actually have installed.

[color=#e06666][size=5][b]New in v2.7 -- the tools tell you WHICH mod moved[/b][/size][/color]

Every tool here refuses to answer from stale data rather than hand you a confidently wrong number. That was the right behaviour and it was [i]exasperating[/i]: it told you the world had changed, never [b]what[/b] changed. Localising a single updated mod took nine investigative steps.

[b][font=Courier New]x4modlist changed[/font][/b] now answers it directly, and [font=Courier New]x4modlist snapshot[/font] gives you a baseline to compare against.

[b]Two things it can now see that it genuinely could not before.[/b] A mod whose [i]files[/i] changed while its [font=Courier New]content.xml[/font] stayed put -- which is the ordinary "edit the file, copy it in" workflow -- was completely invisible: measured on a real 121-mod list, [b]72 of them[/b] had at least one file newer than their own manifest, and every tool reported FRESH while describing a different set of mods. That failed in the unsafe direction. So did a mod enabled or disabled in the game's own mod menu, because toggling rewrites only the profile manifest.

[i]Also in this release:[/i] a stale-data warning that named a command the release did not actually ship (it ships now); stale warnings that show both fingerprints, so "how far did it move?" is answerable without writing a script; and a set of fixes to the toolkit's own self-check -- the one that deliberately breaks the code to confirm the tests notice. It could not restore the tree if it was killed mid-run, and it silently measured a narrower scope than it reported. While it runs, every tool now warns that it is answering from deliberately broken code, and anything that would write data refuses outright.

[color=#e06666][size=5][b]New in v2.6 -- ask questions across every file at once[/b][/size][/color]

[b]BaseX corpus search now ships with the toolkit[/b] (it was internal until now). It indexes the whole corpus -- base game, every DLC, and every installed mod, 36 million nodes -- and answers in about a second the class of question a recursive grep answers [i]dishonestly[/i].

[b]The specific thing it fixes:[/b] "nothing references this macro" is the most dangerous sentence in modding, because a grep cannot tell [i]this does not exist[/i] from [i]I did not look everywhere[/i] -- and roughly 62% of mod XML lives inside packed archives a grep never opens. So it refuses to print a zero as a finding unless it can state the denominator it looked over, and then says [b]"NEGATIVE CONFIRMED over N of M documents"[/b] with every exclusion named. It also refuses to answer at all from an index that has gone stale, rather than handing you a confidently wrong number.

Two indexes: [font=Courier New]x4raw[/font] (every file [i]as written[/i]) and [font=Courier New]x4eff[/font] (the merged tree the game actually sees, diffs applied in load order). Use the second for any claim about a live value -- the first will happily quote a vanilla number your modlist overwrote.

[b]Be honest with yourself about the cost before you start:[/b] it needs Java 17+, about 3 GB of disk, and a one-off build measured in minutes rather than seconds. BaseX itself is bundled (BSD-3-Clause), so there is nothing extra to download. It is entirely optional -- the rest of the toolkit does not need a JVM.

[i]Also in this release:[/i] a preflight so the first run tells you what is actually wrong -- a missing JVM used to surface as [font=Courier New]BaseX query failed: [WinError 2][/font], blaming BaseX for a missing Java, and an unbuilt index printed a raw error that never once named the build script. And the Linux test failures are fixed (all eight were test-side, not library defects), though Linux remains explicitly [i]not[/i] a supported guarantee -- see the honesty note below.

[color=#e06666][size=5][b]The Tools -- and What Each One Does For You[/b][/size][/color]

Eleven command-line tools are bundled and pre-wired. No need to stress if it looks like a foreign language--Claude drives them for you as it needs them; though you can also run them yourself. They all read [b]packed[/b] mods ([font=Courier New].cat[/font]/[font=Courier New].dat[/font], VRO included) as well as loose ones.

[size=4][color=#e06666]x4validate[/color] -- the flagship: catch the silent no-op before you launch[/size]
[list]
[*][b]Every diff [font=Courier New]sel=[/font] is resolved against the real merged tree[/b] (base + all DLC + your enabled mods), so a patch that matches nothing is an [i]error[/i], not a clean pass.[/*]
[*][b]References are checked[/b] -- every ware, macro and [font=Courier New]{page,t}[/font] text id your mod introduces must point at something real.[/*]
[*][b]Completeness[/b] -- compare new content against a vanilla analogue and answer "did I forget a spot?" before the ware turns up priceless and unbuyable.[/*]
[*][b][font=Courier New]--tier b[/font][/b] merges your [i]installed[/i] modlist in load order, so cross-mod patches resolve for real -- and it catches the failure that looks like success: content [b]another mod removed[/b]. (Real case from development: one mod removes a vanilla macro and never re-adds it, orphaning it for six other mods -- 415 engine errors that base+DLC validation calls fine.)[/*]
[*][b]It models the X4 patch rules a naive XML merge gets wrong[/b], each of which otherwise produces a silent no-op: a [font=Courier New]sel=[/font] matching multiple nodes applies [b]nothing[/b] (RFC 5261 -- 236 such ops were silently skipped across one real modlist), [font=Courier New]if=[/font] guards gate an op before the selector, and [font=Courier New]extensions/<target>/<rel>[/font] paths belong to that mod, not the base game.[/*]
[*][b]Validated against the engine, not against itself[/b] -- a test harness replays every patch op X4's own log rejected and requires the same verdict (the bar is zero disagreements and zero false OKs; the count is whatever your own log and modlist produce).[/*]
[/list]
[size=4][color=#e06666]x4effective[/color] -- "xEdit for X4": every final value, and who set it[/size]
The effective value of every ware, macro and job across base + DLC + all your mods, with [b]per-attribute provenance[/b] ([font=Courier New]base -> modA -> modB[/font]) in a queryable store. Read one column across everything ("all missiles and their damage"), see the full record, get just the who-set-it chain, list everything a single mod wins, or dump the live merged XML for any path. Stop guessing which mod actually won.

[size=4][color=#e06666]x4compat[/color] -- what breaks if I install this?[/size]
Collision detection over the effective tree: two mods editing the same node (one silently loses), defining the same registry id, fully overriding the same file, or -- the sneaky one -- a later mod [b]replacing a whole element[/b] and wiping every earlier mod's edits inside it. Candidate mode answers "what would this new mod collide with?" [i]before[/i] you install it.

[size=4][color=#e06666]x4xref[/color] -- who calls this? who listens?[/size]
A who-calls / who-listens / cue index over every Mission Director and AI script in base + DLC + your mods. "Does anything else react to this event?" in one query, instead of many rounds of grepping for tokens that share no keyword with what you're actually asking.

[size=4][color=#e06666]x4stats[/color] -- is this balanced against MY game?[/size]
Advisory numeric comparison: how a mod's ware/weapon pricing and stats sit against everything else in [i]your[/i] effective game, including an installed overhaul's rescaled values. Grounds a balance discussion; doesn't pretend to settle one.

[size=4][color=#e06666]x4similar[/color] -- do I already have this ship?[/size]
Advisory near-duplicate detection: flags a mod's ship as likely "the same ship" you already have under a different name and id, filtered by class and purpose.

[size=4][color=#e06666]x4modlist[/color] -- triage your whole modlist[/size]
A registry of your installed mods built from what's [b]physically installed[/b] (each mod's own manifest -- folder names lie), cross-checked against your profile. With the optional Nexus API key it pulls upstream versions, update dates, changelogs and status, then sorts everything into lanes: ready / churning / predates your game version / custom-local / dropped-by-the-author.

[size=4][color=#e06666]x4diff[/color] -- separate your edits from the author's[/size]
Semantic XML diff between two versions of a mod, with multi-baseline support -- built for the "I modified this mod months ago and the author just updated it" problem.

[size=4][color=#e06666]x4debug[/color] -- what did the ENGINE actually complain about?[/size]
Turns X4's own [font=Courier New]debug.txt[/font] into a triage: every error line bucketed and attributed to a mod, with the buckets required to sum to the input so nothing is quietly dropped. Crosscheck mode compares what the engine skipped against what the validator predicted, [i]per item[/i] -- and "the engine hit it but we never predicted it" is a validator blind spot, which is how a fair number of the fixes in this changelog were found.

[size=4][color=#e06666]x4save[/color] -- what would I actually lose if I removed this mod?[/size]
Reads a savegame and reports what is baked into it. Worth having because the failure mode is silent: the engine deletes content orphaned by a removed mod without complaining, so the save looks fine right up until it doesn't.

[size=4][color=#e06666]x4live[/color] -- ask the running game[/size]
A live channel to an actual running session, through a small bundled game extension. Every other tool here reasons about what the merged tree should produce; this reads what the engine did produce. Entirely optional -- and it is the only part of the toolkit that puts an extension in your game folder.

[size=4][color=#e06666]BaseX corpus search[/color] -- the superweapon: what does this look like across EVERYTHING?[/size]
XQuery over the whole indexed corpus, for the questions that span files rather than living in one: what values does this attribute take across every ship? who references this macro? which mods define a ware nobody produces? It is the only tool here that can back a [i]negative[/i], because it states the denominator it searched. Optional -- needs Java 17+ and a one-off index build.

[color=#e06666][size=5][b]FAQ[/b][/size][/color]
[b]Q: Which game versions / DLC does it support?[/b] The knowledgebase targets X4 v7.x-v9.x and includes the 7.x->9.0 migration map. All DLC is supported; just tell Claude your version and what you have installed.
[b]Q: Do I need to know how to code?[/b] No. You describe what you want in plain English; Claude does the XML. The tools exist to catch its mistakes as much as yours.
[b]Q: Can Claude break my mods or saves?[/b] The safety hooks should prevent it -- Claude can't write to your reference tree or directly edit .cat/.dat, must ask permission for mod/profile edits, and backs everything up with an audit log. But LLMs are probabilistic; keep your own backups too (X4 saves especially).
[b]Q: Do I have to unpack the base game?[/b] Only for x4validate's full cross-reference power. You can start without it; setup walks you through unpacking with XRCatTool when you're ready.
[b]Q: Does it work with VRO / big overhauls?[/b] Yes -- and that's rather the point. The tools read packed mods, so an overhaul's rescaled values show up in the effective tree, in balance comparisons, and in collision checks.
[b]Q: "jq not found"?[/b] Run [font=Courier New]winget install jqlang.jq[/font] and restart Claude Code.
[b]Q: How do I update the toolkit?[/b] Download the new version and re-run the installer (or extract over the old one). Your knowledgebase additions are preserved.
